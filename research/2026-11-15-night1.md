# Night 1 (15–16 Nov 2026): from 1,430 to 3,254 tok/s prefill

**Setup.**
- **Hardware:** one RTX 5090 Laptop GPU (mobile GB203, 24 GB, 896 GB/s, 175 W) in an Olares One running Proxmox. The model server runs in an Ubuntu 24.04 LXC with 8 cores and 64 GB RAM.
- **Workload:** one user, agent-shaped: 17–47K-token prompts with 20 tools, English plus Swedish.
- **Starting point:** llama.cpp f8def7f (10 Aug 2026, Glimmer's launch day) with unsloth UD-Q4_K_XL, Meta's DFlash drafter at depth 15, f16 KV, vision projector and 131K context.

Every speed number comes from the same harness ([`bench/gbench.py`](../bench/gbench.py)) on the same GPU; raw data is in [`results/`](../results/).

## 2. Prefill hits a power ceiling

**Batch size and drafter barely move it** (llama.cpp master, K-quants):

| Change | Prefill effect |
|---|---|
| Prompt batch 512 → 1024 → 2048 | +2–4% |
| DFlash drafter on/off | about 3% |
| Best case, no drafter, no vision, batch 2048 | 1,848 tok/s at 6.9K |

**The GPU log shows why:** throttle reason 0x4 (software power cap) on almost every sample, at 116–176 W, 1.6–2.0 GHz and 70–88 °C, with the memory clock steady at 14 GHz. Prefill is limited by power. Only work per watt helps, which on Blackwell means FP4 tensor cores.

## 4. FP4 prefill and the NVFP4 quality problem

**llama-quantize's NVFP4 is fast but lossy.** NVFP4 on all linear layers via `--tensor-type …=nvfp4` reached **4,609 tok/s** prefill (pp512) at 16.0 GB, but KLD was 0.180 on agent text, against 0.033 for UD-Q4_K_XL. Scoring it with 8-bit activations (`GGML_CUDA_MMQ_PREC=q8`) gave 0.164, so the loss is mostly in the weights.

**The cause** is in `quantize_row_nvfp4_ref`:
- The UE4M3 block scale is set straight from the 16-value block maximum, and there is no per-tensor global scale.
- Glimmer's weights have max |W| of about 0.07–0.25, so most scales land in UE4M3's subnormal range (multiples of 2^-9), with very few significant bits.
- It also ignores the imatrix.

**Our fix, [`tools/q_nvfp4.py`](../tools/q_nvfp4.py):**
- per-tensor G = max|W| / (6 · 448), written as `<tensor>.scale`;
- each block scale chosen among 4 nearby codes by imatrix-weighted squared error.

Weighted relative error on four tensors of layer 10:

| Tensor | llama-quantize | Ours: G, nearest code | Ours: G + importance search |
|---|---:|---:|---:|
| ffn_up | 0.0183 | 0.0105 | 0.0078 |
| ffn_down | 0.0178 | 0.0100 | 0.0068 |
| attn_q | 0.0185 | 0.0101 | 0.0051 |
| attn_gate | 0.0173 | 0.0103 | 0.0046 |

**For llama.cpp to use the scales,** the Glimmer graph has to apply them to the attention gate and the MLP ([patch 0001](../patches/llama.cpp/0001-muse-glimmer-apply-nvfp4-per-tensor-scales-on-gate-and-ffn.patch)). Q, K, V and the output projection already did. With the patch:
- the per-tensor-scale build reaches KLD **0.073**;
- **GPTQ** ([`tools/gptq_nvfp4.py`](../tools/gptq_nvfp4.py)) reaches **0.059**, at the same speed. It runs layer by layer through the BF16 model with transformers 5.23, on 128 × 2048 tokens of Glimmer-format agent text plus Swedish, and takes 29 minutes.

**Splitting the GPTQ build's error:** with 8-bit activations its KLD is 0.041, so the FP4 activations add about 0.03. Marking the sensitive kinds for 8-bit activations through llama.cpp's `general.tensor_extra.prec_a4` metadata ([`tools/add_prec.py`](../tools/add_prec.py)):

| GPTQ NVFP4, 8-bit activations on | Prefill 512 / 4096 | KLD agent / English / Swedish |
|---|---:|---|
| nothing | 4,559 / 4,286 | 0.059 / 0.036 / 0.038 |
| ffn_down | 3,188 / 2,908 | 0.054 / 0.031 / 0.031 |
| ffn_down + attn_output | 2,991 / 2,743 | 0.046 / 0.028 / 0.028 |
| all attention + ffn_down | 2,662 / 2,434 | 0.041 / 0.025 / 0.026 |

NVFP4 with 8-bit activations runs at about 1,600 tok/s, below IQ4_XS (about 2,200) at better weight quality. So tensors that need 8-bit activations are better off as IQ4_XS. That gives the hybrids, built with [`tools/merge_nvfp4.py`](../tools/merge_nvfp4.py): GPTQ-NVFP4 tensors from the GPTQ build, everything else IQ4_XS with the agent imatrix.

| Hybrid | Prefill 512 / 4096 | KLD agent / English / Swedish |
|---|---:|---|
| gate+up NVFP4 | 3,055 / 2,930 | 0.047 / 0.024 / 0.027 |
| gate+up+attention NVFP4 | 3,537 / 3,356 | 0.055 / 0.030 / 0.032 |
| whole MLP NVFP4 | 3,754 / 3,650 | 0.053 / 0.030 / 0.034 |

## 5. NVFP4 with drafting: the verify kernel

**The hybrids lost decode under DFlash.** At depth 7 the gate+up hybrid decoded 88.5 / 86.6 against 107.1 / 103.9 for UD-Q4_K_XL, with the same acceptance.

**The cause was one batch size.** `llama-bench -p 1..64` shows the hybrid's matmul time jumping at batch 8:

| Batch | 1 | 4 | **8** | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|
| UD-Q4_K_XL, ms | 21.0 | 25.6 | **24.2** | 28.9 | 33.8 | 44.7 |
| hybrid gate+up, ms | 20.3 | 25.7 | **31.8** | 27.0 | 29.8 | 35.1 |

On Blackwell, `ggml_cuda_should_use_mmvq` keeps every type without a tuned entry on the vector kernel up to 8 columns. Q4_K moves to the few-row MMQ kernel after 5. [Patch 0002](../patches/llama.cpp/0002-cuda-mmvq-nvfp4-uses-mmq-from-5-columns-on-blackwell.patch) gives NVFP4 a limit of 4 columns, after which batches 5–9 take about 25.5 ms.

**After the patch** (chat greedy / sampled, prefill at 6.9K / 101K):

| Setup | Depth 7 | Depth 15 | Prefill |
|---|---:|---:|---:|
| hybrid gate+up | 103.4 / 102.6 | 107.3 / 103.6 | 2,698 / 2,044 |
| hybrid gate+up+attention | 99.3 / 95.6 | 99.2 / 99.3 | 3,014 / 2,234 |
| **hybrid MLP** | 103.9 / 102.7 | **110.3 / 105.4** | **3,254 / 2,367** |
| GPTQ all-NVFP4 | — | 102.7 / 99.5 | 3,854 / 2,644 |

## 7. Notes for anyone repeating this

- **Unwanted tools flag:** llama.cpp master refuses `--tools all` on a network address without `--api-key` or `--allow-unauthenticated-tools`.
- **Prompt cache with vision:** with `--mmproj` loaded, `--cache-reuse` is disabled. Agent prompts are reused through context checkpoints and `--cache-ram`.
- **Reasoning strength:** Glimmer's template ignores `reasoning_effort`. Set `reasoning_strength` once, through `LLAMA_ARG_CHAT_TEMPLATE_KWARGS`. It sits in the system turn, so changing it per request breaks the cache.
- **Converter:** `convert_hf_to_gguf.py` needs transformers 5.x for Glimmer's `TokenizersBackend` tokenizer class.
- **Building NInferno master** needs the FFmpeg development libraries and `cuda-nvtx`.
- **Disk:** quantization experiments with a 56 GB BF16 GGUF and a 30 GB Q8_0 reference fill a 400 GB disk quickly. Delete templates after merging.
